# 7. Spring Cloud: Monitoring Performance & Best Practices
## **Mục tiêu buổi học**

Sau buổi này, học viên cần biết cách **quan sát, phát hiện, điều tra và xử lý sự cố production** cho một hệ thống Spring Cloud/microservices.

Kết thúc buổi học, học viên có thể:

- Phân biệt **logs, metrics và traces**.
- Cấu hình Spring Boot Actuator + Micrometer để expose metrics.
- Thiết kế dashboard cho Gateway, Order Service, Kafka và database.
- Theo dõi p50/p95/p99, error rate, throughput, saturation.
- Biết metric nào quan trọng cho JVM, HTTP, DB pool, circuit breaker, Kafka/DLQ/outbox.
- Truy vết một request qua Gateway → Order → Inventory → Payment bằng trace/correlation ID.
- Nhận diện performance anti-pattern phổ biến.
- Viết alert có action/runbook, không tạo alert noise.

Spring Boot mô tả observability gồm ba trụ cột: **logging, metrics và traces**. Actuator dùng Micrometer Observation làm nền tảng cho metrics/traces, và hỗ trợ tích hợp OpenTelemetry. (docs.spring.io)

# **2. Logs, Metrics và Traces khác nhau thế nào?**

| **Thành phần** | **Trả lời câu hỏi** | **Ví dụ** |
| --- | --- | --- |
| **Logs** | Chính xác lỗi gì đã xảy ra? | `Payment timeout for order ORD-123` |
| **Metrics** | Hệ thống có xu hướng bất thường không? | p95 checkout tăng, 5xx tăng, Kafka lag tăng |
| **Traces** | Một request đã đi qua đâu và chậm/lỗi ở bước nào? | Gateway → Order → Inventory → Payment |

## **2.1 Logs**

Log cần có cấu trúc, không chỉ là text tự do.

Ví dụ log tốt:

`{
  "timestamp": "2026-10-20T20:07:12.123Z",
  "level": "ERROR",
  "service": "order-service",
  "traceId": "a8f37e9c",
  "orderId": "ORD-123",
  "tenantId": "tenant-01",
  "event": "PAYMENT_STATUS_UNKNOWN",
  "message": "Payment response timed out after gateway request was accepted"
}`

Không nên log:

`- Password.
- Access token/JWT.
- Credit card number.
- CVV.
- Full bank account.
- Payload nhạy cảm không cần thiết.`

## **2.2 Metrics**

Metric là dữ liệu số theo thời gian, dùng để:

`- Vẽ dashboard.
- Theo dõi xu hướng.
- Đặt alert.
- So sánh trước/sau deploy.
- Phát hiện saturation/bottleneck.`

Micrometer là facade metrics mà Spring Boot Actuator auto-configure; Spring Boot có thể export metrics ra Prometheus, OTLP và nhiều backend khác. Endpoint `/actuator/prometheus` cần được expose để Prometheus scrape. (docs.spring.io)

## **2.3 Traces**

Trace biểu diễn toàn bộ lifecycle của một request.

`Trace ID: a8f37e9c

Gateway                    20ms
  └── Order Service        850ms
        ├── Inventory      620ms
        ├── Payment        180ms
        └── PostgreSQL      30ms`

Trace giúp trả lời:

`- Request nào chậm?
- Service nào chậm?
- Dependency nào chậm?
- Call nào timeout?
- Request nào liên quan customer complaint?`

Spring Boot Actuator hỗ trợ Micrometer Tracing; các tracer được auto-configure phổ biến gồm OpenTelemetry với OTLP và Brave với Zipkin. (docs.spring.io)

# **3. Các metric bắt buộc cần theo dõi**

## **3.1 HTTP/API Metrics — RED Method**

RED là nhóm metric dành cho request-driven service:

`R — Rate
E — Errors
D — Duration`

| **Metric** | **Ý nghĩa** | **Ví dụ alert** |
| --- | --- | --- |
| Request rate | Bao nhiêu request/giây | Traffic tăng đột biến |
| Error rate | Bao nhiêu request lỗi | 5xx > 1% trong 5 phút |
| Duration | p50/p95/p99 latency | p95 checkout > 800ms |
| In-flight requests | Số request đang xử lý | Tăng liên tục, không giảm |
| Status distribution | 2xx/4xx/5xx | 429 hoặc 503 tăng bất thường |

Ví dụ requirement cho Order Service:

`POST /orders:
- p95 < 800ms.
- p99 < 2s.
- 5xx < 1%.
- Checkout success rate > 99%.`

> Không chỉ dùng average latency. p95/p99 phản ánh nhóm user có trải nghiệm chậm nhất.
> 

Micrometer `Timer` ghi nhận số event và tổng thời gian; timers/distribution summaries có thể thu thập phân phối percentile. Counter nên được quan sát theo **rate trên khoảng thời gian**, thay vì chỉ nhìn tổng số tích lũy từ lúc app khởi động. (docs.micrometer.io)

---

## **3.2 JVM Metrics**

| **Metric** | **Ý nghĩa** | **Dấu hiệu cần điều tra** |
| --- | --- | --- |
| Heap used / max | Mức dùng heap | Heap tăng liên tục, không giảm sau GC |
| Heap after GC | Memory còn giữ sau GC | Có thể memory leak/cache unbounded |
| GC pause | Thời gian JVM bị pause | p99 API tăng cùng GC pause |
| Allocation rate | Tốc độ tạo object | Tạo object quá nhiều, GC pressure |
| Thread count | Số thread | Tăng bất thường, thread leak |
| Thread states | RUNNABLE/BLOCKED/WAITING | Nhiều thread chờ external API/DB |
| CPU usage | Tải CPU | CPU cao kéo dài/saturation |
| Process uptime/restart count | Tính ổn định | Pod restart/OOMKill |

Ví dụ cần suy luận:

`p99 checkout tăng lên 10 giây.
CPU chỉ 40%.
Heap ổn định.
300 thread đang WAITING ở HTTP client.

→ Khả năng cao là I/O/dependency bottleneck,
không phải CPU hay memory bottleneck.`

---

## **3.3 Database & Connection Pool Metrics**

| **Metric** | **Ý nghĩa** | **Dấu hiệu nguy hiểm** |
| --- | --- | --- |
| DB CPU | Tải database | Cao kéo dài gần saturation |
| DB I/O | Đọc/ghi disk | I/O wait tăng |
| Slow query count | Số query chậm | Query/index/N+1/lock issue |
| Active connections | Connection đang dùng | Gần max pool |
| Pending/waiting connections | Request chờ connection | Pool exhaustion |
| Query duration | Thời gian query | p95 DB query tăng |
| Lock wait/deadlock | Contention | Transaction dài/lock strategy sai |
| Cache hit rate | DB/cache effectiveness | Cache miss tăng gây DB overload |

Câu cần hỏi khi API chậm:

`- Application CPU có cao không?
- DB CPU/I/O có cao không?
- Connection pool có đầy không?
- Slow query có tăng không?
- Có lock wait/deadlock không?
- Query count trên mỗi request có tăng không?`

---

## **3.4 Kafka, Outbox và DLQ Metrics**

| **Metric** | **Ý nghĩa** | **Alert gợi ý** |
| --- | --- | --- |
| Consumer lag | Consumer chậm hơn producer bao nhiêu | Lag tăng liên tục |
| Consumer throughput | Tốc độ xử lý event | Thấp hơn expected |
| Processing error rate | Tỷ lệ consumer fail | Tăng đột biến |
| Retry count | Số lần retry event | Dependency hoặc message issue |
| DLQ count | Message bị xử lý thất bại | Bất kỳ message payment/order critical nào |
| Outbox pending count | Event chưa publish | Tăng kéo dài |
| Oldest outbox age | Event cũ nhất chưa publish | Vượt ngưỡng business SLA |
| Duplicate event detected | Event đã xử lý lặp | Producer/consumer retry pattern bất thường |

Ví dụ:

`Order = CONFIRMED nhưng Notification chưa gửi.

Cần kiểm tra:
1. Outbox có record OrderConfirmed chưa?
2. Outbox publisher có publish Kafka chưa?
3. Kafka topic có message không?
4. Consumer lag bao nhiêu?
5. Consumer có retry/DLQ không?
6. EventId đã bị deduplicate nhầm không?`

---

## **3.5 Resilience Metrics**

Với Resilience4j/Spring Cloud Circuit Breaker, cần theo dõi:

| **Metric** | **Ý nghĩa** |
| --- | --- |
| Circuit breaker state | Closed / Open / Half-open |
| Failed calls | Lỗi downstream |
| Slow calls | Dependency quá chậm |
| Retry attempts | Có retry storm không |
| Bulkhead available concurrency | Resource còn lại |
| Bulkhead rejection count | Request bị từ chối do giới hạn |
| Timeout count | Downstream timeout |
| Fallback count | Hệ thống đang degrade bao nhiêu |

Ví dụ:

`Inventory circuit breaker OPEN
→ Không nên chỉ coi là lỗi kỹ thuật.
→ Cần biết bao nhiêu checkout bị từ chối hoặc pending reservation.`

# **5. Alert Design**

Alert tốt phải trả lời được:

`- Alert này có ảnh hưởng user/business không?
- Ai xử lý?
- Xử lý bước đầu thế nào?
- Alert có đủ signal để không bị false positive không?`

## **Ví dụ alert tốt**

| **Alert** | **Điều kiện** | **Severity** | **First response** |
| --- | --- | --- | --- |
| Checkout reliability degraded | Checkout success rate < 99% trong 5 phút | **Critical** | Kiểm tra Gateway, Order error rate, Inventory/Payment trace |
| Checkout latency high | p95 `POST /orders` > 800ms trong 10 phút | **Warning/Critical** | Kiểm tra downstream latency, DB pool, circuit breaker |
| Payment-order mismatch | `payment_success_order_pending` > 0 hoặc vượt baseline | **Critical** | Tạm dừng unsafe retry, chạy reconciliation |
| Outbox backlog | Oldest unpublished event > 5 phút | **Critical** | Kiểm tra outbox publisher/Kafka |
| Kafka lag growing | Consumer lag tăng liên tục 10 phút | **Warning** | Kiểm tra consumer errors/throughput/pod capacity |
| DLQ received critical event | DLQ count > 0 cho payment/order topic | **Critical** | Triage message, không replay mù quáng |
| DB pool exhaustion | Pending DB connections > 0 kéo dài | **Warning** | Check slow query, locks, pool config |
| Circuit breaker open | Inventory CB open > 2 phút | **Warning/Critical** | Kiểm tra Inventory; assess checkout impact |

## **Anti-pattern alert**

`- CPU > 80% một lần là page ngay.
- Heap > 70% là page ngay.
- Một 404 là page ngay.
- Log có chữ ERROR là page ngay.`

Các alert này thường gây noise. Cần đặt theo:

`- Rate.
- Duration.
- Business impact.
- Correlation với signal khác.`

## **6.1 Đo trước, tối ưu sau**

> 
> “Chắc phải scale pod.”

> “Chắc database chậm.”
> 

Nên dùng evidence:

`Symptom
  ↓
Metrics
  ↓
Trace
  ↓
Logs / profiler / thread dump
  ↓
Root-cause hypothesis
  ↓
Fix
  ↓
Load test / monitor lại`

---

## **6.2 Tránh High Cardinality Metrics**

Metric tags không được chứa giá trị quá đa dạng.

Không nên:

`http_request_total{userId="U-123"}
http_request_total{orderId="ORD-001"}
http_request_total{email="a@example.com"}`

Vì mỗi `userId`, `orderId`, `email` tạo thêm time series mới, có thể làm monitoring backend quá tải.

Nên:

`http_request_total{
  service="order-service",
  endpoint="/orders",
  method="POST",
  status="201"
}`

Nếu cần điều tra một order cụ thể:

`- Dùng trace ID.
- Dùng structured logs.
- Không dùng metric tag bằng orderId.`

Micrometer dùng mô hình metric có dimensions/tags; meter được nhận diện bởi metric name và dimensions, vì vậy cần kiểm soát tag để có thể drill-down mà không tạo quá nhiều time series. (docs.micrometer.io)

---

## **6.3 Theo dõi đúng loại Metric**

| **Cần đo** | **Dùng metric phù hợp** |
| --- | --- |
| Số payment thành công | Counter |
| Thời gian checkout | Timer |
| Số request đang xử lý | Gauge |
| Kích thước payload | DistributionSummary |
| Job batch chạy lâu | LongTaskTimer |

Micrometer có các meter primitives như `Timer`, `Counter`, `Gauge`, `DistributionSummary` và `LongTaskTimer`; Timer đo cả count và tổng thời gian, còn DistributionSummary dùng cho phân bố giá trị không phải thời gian, như payload size. (docs.micrometer.io)

---

## **6.4 Không Log Quá Nhiều**

Không nên:

Java

`log.info("Request body: {}", request);
log.info("Response body: {}", response);`

với mọi request production.

Rủi ro:

`- Tăng I/O.
- Tăng storage cost.
- Lộ PII/payment data.
- Khó tìm thông tin quan trọng trong log noise.`

Nên:

`- Log event quan trọng.
- Có traceId/correlationId.
- Log structured fields.
- Log error với context đủ dùng.
- Mask dữ liệu nhạy cảm.
- Sampling log nếu traffic cao.`

---

## **6.5 Không Dùng `.block()` Trong WebFlux Request Path**

Nếu service dùng Spring WebFlux:

Java

`webClient.get()
    .uri("/inventory")
    .retrieve()
    .bodyToMono(InventoryResponse.class)
    .block();`

Đây là blocking call.

Rủi ro:

`- Block event-loop.
- Khi load tăng, request queue tăng.
- p99 latency tăng mạnh.
- WebFlux mất lợi ích non-blocking.`

Nếu dùng JPA/JDBC blocking, cân nhắc:

`- Dùng Spring MVC cho CRUD blocking thông thường; hoặc
- Dùng R2DBC/end-to-end non-blocking khi thật sự cần; hoặc
- Cô lập blocking work khỏi event-loop như giải pháp chuyển tiếp,
  có giới hạn resource rõ ràng.`

# **7. Cấu hình Spring Boot cơ bản**

## **Dependencies**

**pom.xml**

```
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-actuator</artifactId>
    </dependency>
```

## **Actuator và Prometheus**

**application.yml**v3

```
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
```

Sau đó có thể kiểm tra:

`GET /actuator/health
GET /actuator/metrics
GET /actuator/metrics/http.server.requests
GET /actuator/prometheus`

Spring Boot cung cấp endpoint `metrics` để xem các meter có trong app và endpoint `prometheus` để expose dữ liệu theo định dạng Prometheus khi có registry phù hợp trên classpath và endpoint được expose. (docs.spring.io)

> Lưu ý: tỷ lệ trace sampling là quyết định vận hành. Không nên mặc định trace 100% mọi request ở production traffic lớn mà chưa đánh giá chi phí và nhu cầu điều tra.

# **10. Incident Drill**

## **Scenario**

`Inventory Service bị chậm 3 giây trong 20% requests.

Observed symptoms:
- Checkout p95: 300ms → 1.8s.
- Checkout p99: 700ms → 6s.
- Retry count tăng.
- Inventory circuit breaker bắt đầu Half-open/Open.
- Get Order vẫn phải giữ p95 < 300ms.`

## **Học viên cần trả lời**

`1. Alert nào cần fire đầu tiên?
2. Dashboard nào xem trước?
3. Trace nào giúp xác minh Inventory là dependency chậm?
4. Retry có đang làm traffic tệ hơn không?
5. Get Order có bị ảnh hưởng không? Nếu có, bulkhead sai ở đâu?
6. Immediate mitigation là gì?
7. Long-term fix là gì?`
