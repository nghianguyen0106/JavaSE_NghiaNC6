# 3. Spring Cloud Stream Kafka Outbox Idempotency & DLQ
## Mục tiêu

Biết xây event-driven flow an toàn khi event duplicate, consumer lỗi hoặc publisher crash.

## Câu chuyện

Order được confirm thành công:

`Order = CONFIRMED`

Sau đó hệ thống cần:

`- Gửi email.
- Ghi audit.
- Cập nhật analytics dashboard.`

Code cũ:

`Save Order DB
    ↓
Publish Kafka Event`

Failure window:

`- DB commit thành công.
- Application crash trước khi publish Kafka event.
- Order confirmed nhưng email/audit/analytics không chạy.`

---

## Cần học

### 1. Event-driven Flow

Phân biệt:

`Command:
ReserveInventory
ChargePayment

Event:
OrderCreated
InventoryReserved
PaymentSucceeded
OrderConfirmed`

Event envelope nên có:

`- eventId
- eventType
- aggregateId
- aggregateType
- occurredAt
- schemaVersion
- payload`

### 2. Spring Cloud Stream

Tìm hiểu functional model:

`Supplier  → publish event
Function  → consume rồi transform event
Consumer  → consume event`

Tìm hiểu thêm:

`- Binding.
- Topic/destination.
- Consumer group.
- Partition.
- Retry.
- Error channel.
- Dead Letter Queue.`

Spring Cloud Stream hỗ trợ mô hình binding giữa application và message middleware; Kafka binder hỗ trợ retry/error handling và cấu hình DLQ theo consumer binding. (docs.spring.io)

### 3. Transactional Outbox

Hiểu dual-write problem:

`Sai cách:
Save database
→ publish event

Vì có thể:
- DB success nhưng publish fail.
- Publish success nhưng DB fail.`

Outbox flow:

`BEGIN TRANSACTION
  INSERT INTO orders
  INSERT INTO outbox_events
COMMIT

Outbox Publisher / CDC
  ↓
Kafka`

### 4. Idempotent Consumer

Kafka/message broker thường hướng tới at-least-once delivery trong nhiều flow thực tế, nên consumer phải sẵn sàng nhận event lặp.

Ví dụ:

`Event: OrderConfirmed
eventId: evt-001`

Consumer cần đảm bảo:

`Nếu evt-001 đã xử lý:
→ Không gửi email lần hai.
→ Không tạo audit record trùng.
→ Không update analytics sai.`

### 5. DLQ

DLQ không phải nơi “ném lỗi vào rồi quên”.

Cần có:

`- Lý do vào DLQ.
- Retry đã chạy bao nhiêu lần.
- Người/team chịu trách nhiệm.
- Cách sửa dữ liệu/message.
- Cách replay có kiểm soát.`

---

## Thực hành

Tạo event:

`OrderConfirmed`

Có ba consumer:

`- Notification Consumer.
- Audit Consumer.
- Analytics Consumer.`

Yêu cầu:

`- Event có eventId.
- Notification Consumer không gửi email duplicate.
- Chủ động làm một consumer throw exception.
- Quan sát retry.
- Sau khi retry hết, message vào DLQ.
- Viết kế hoạch replay DLQ.`
