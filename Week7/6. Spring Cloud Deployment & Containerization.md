# 6. Spring Cloud: Deployment & Containerization
## **Mục tiêu buổi học**

Sau buổi này, học viên cần biết cách đóng gói và triển khai một Spring Boot/Spring Cloud service theo hướng production-ready:

- Build Docker/OCI image cho Spring Boot service.
- Chạy service bằng Docker Compose cùng dependency như PostgreSQL/Kafka.
- Externalize configuration theo môi trường.
- Phân biệt ConfigMap và Secret khi deploy Kubernetes.
- Cấu hình Actuator health check, liveness và readiness.
- Hiểu rolling deployment, canary và rollback.
- Thiết kế database migration tương thích giữa version cũ và mới.
- Không đưa secret vào source code hoặc Docker image.

Spring Boot hỗ trợ tạo OCI/Docker-compatible image bằng Dockerfile hoặc Cloud Native Buildpacks; Maven/Gradle đều có hỗ trợ build image trực tiếp. (docs.spring.io)

# **1. Câu chuyện thực tế**

Order Service đang chạy trong flash sale platform:

`Client
  ↓
API Gateway
  ↓
Order Service
  ├── PostgreSQL
  ├── Kafka
  ├── Inventory Service
  └── Payment Service`

Team cần bổ sung trạng thái payment chi tiết hơn.

`Old order status:
- PENDING
- CONFIRMED
- CANCELLED

New order status:
- PENDING_PAYMENT
- PAYMENT_PROCESSING
- CONFIRMED
- PAYMENT_FAILED
- CANCELLED`

Team dự định làm như sau:

`1. Drop cột status cũ.
2. Tạo schema/status mới.
3. Build Docker image mới.
4. Rolling deploy toàn bộ pods.
5. Nếu lỗi thì rollback image cũ.`

Nhưng cách này có rủi ro:

`- Trong rolling deployment, version cũ và version mới cùng chạy.
- Version cũ có thể không hiểu status/schema mới.
- Rollback image không khôi phục schema/data đã drop.
- Pod có thể nhận traffic trước khi kết nối DB/Kafka sẵn sàng.
- Nếu liveness probe check DB/Kafka không đúng cách,
  Kubernetes có thể restart hàng loạt pod khi dependency ngoài lỗi.`

> Mục tiêu buổi này: thiết kế deploy sao cho **old version và new version có thể cùng tồn tại**, service chỉ nhận traffic khi sẵn sàng, và rollback không làm hỏng dữ liệu.

# **2. Nội dung cần học**

## **2.1 Containerization: Docker Image cho Spring Boot**

### **Cần hiểu**

Container image nên có các đặc điểm:

`- Reproducible: build lại cho ra artifact nhất quán.
- Nhỏ vừa đủ, không mang source code/build tools vào runtime image.
- Không chạy application bằng root user.
- Không chứa credential/secret.
- Có version/tag rõ ràng.
- Config lấy từ environment/config service/secret store.
- Có graceful shutdown.`

Hai cách phổ biến để tạo image Spring Boot:

| **Cách** | **Khi nên dùng** |
| --- | --- |
| Dockerfile multi-stage | Cần kiểm soát chi tiết build/runtime image |
| Cloud Native Buildpacks | Muốn build nhanh, chuẩn hóa, ít phải tự viết Dockerfile |

Spring Boot Maven/Gradle plugin có thể build OCI image qua Cloud Native Buildpacks. Ví dụ Maven: `mvn spring-boot:build-image`; Gradle: `bootBuildImage`. Buildpacks thường tạo image chạy bằng non-root user. (docs.spring.io)

### **Dockerfile multi-stage mẫu**

**Dockerfile**

```
# ===== Build stage =====
FROM eclipse-temurin:21-jdk AS build

WORKDIR /workspace

COPY mvnw pom.xml ./
```

### **Điểm cần giải thích**

`Build stage:
- Có JDK và Maven wrapper để build artifact.

Runtime stage:
- Chỉ chứa JRE + JAR cần chạy.
- Không cần source code.
- Không cần Maven.
- Chạy non-root user.`

> Không dùng `latest` cho base image ở production; nên pin version/tag hoặc digest theo policy công ty.

Không được để các file như sau lọt vào image/build context:

- private key.
- API token.
- local database dump.
- log chứa data nhạy cảm.`

## **2.3 Configuration: Environment, ConfigMap và Secret**

### **Phân loại configuration**

| **Loại** | **Ví dụ** | **Nơi phù hợp** |
| --- | --- | --- |
| Runtime config | Port, log level, timeout, feature flag | Environment variable / ConfigMap / Config Server |
| Infrastructure config | Kafka host, DB host, service URL | Environment variable / ConfigMap |
| Secret | DB password, Kafka credential, JWT key, API key | Kubernetes Secret / Vault / secret manager |
| Build-time config | JDK version, artifact version | CI pipeline/build config |

Ví dụ:

**application.yml**v1

```
spring:
  application:
    name: order-service

  datasource:
    url: ${DB_URL}
```

Nguyên tắc:

`- Không hard-code DB password trong application.yml.
- Không commit file .env thật vào Git.
- Không nhét secret vào Dockerfile.
- Không log secret ra console.
- Config thay đổi phải có version/owner/review.`

Nếu chạy Kubernetes, Spring Cloud Kubernetes có thể đọc ConfigMap/Secret làm property sources. Cơ chế reload configuration tồn tại, nhưng cần cân nhắc kỹ chiến lược refresh/restart/shutdown và quyền truy cập Kubernetes API; không phải property nào cũng an toàn để thay đổi runtime. (docs.spring.io)

- Không nên giả định service dependency chắc chắn sẵn sàng chỉ vì container đã start.`

## **2.5 Spring Boot Actuator: Liveness và Readiness**

### **Phân biệt**

| **Probe** | **Câu hỏi** | **Kubernetes nên làm gì khi fail?** |
| --- | --- | --- |
| Liveness | App có bị treo/deadlock đến mức cần restart không? | Restart container |
| Readiness | App có sẵn sàng nhận traffic không? | Tạm dừng route traffic vào pod |
| Startup | App khởi động xong chưa? | Đợi trước khi liveness/readiness kiểm tra chặt |

Spring Boot Actuator cung cấp các endpoint health như:

`/actuator/health
/actuator/health/liveness
/actuator/health/readiness`

Khi chạy trên Kubernetes, Spring Boot dùng `ApplicationAvailability` để xuất liveness/readiness health groups. Spring Boot cũng lưu ý không nên gắn liveness với external dependency vì dependency lỗi có thể làm Kubernetes restart hàng loạt application pod, gây cascading failure. (docs.spring.io)

### **Cấu hình mẫu**

**application.yml**v2

```
management:
  endpoint:
    health:
      probes:
        enabled: true
```

### **Quy tắc thảo luận**

`Liveness không nên check:
- Database.
- Kafka.
- Inventory Service.
- Payment Service.

Vì dependency ngoài lỗi không có nghĩa process Order Service đã chết.

Readiness có thể cân nhắc dependency critical,
nhưng phải xem kỹ trade-off:
- Nếu DB unavailable, không nên nhận checkout traffic.
- Nếu Catalog unavailable, có thể vẫn nhận Get Order traffic.
- Không nên biến readiness thành mọi dependency đều phải healthy,
  nếu không outage một service kéo toàn platform mất traffic.`

## **2.7 Rolling Deployment, Canary và Rollback**

### **Rolling deployment**

Kubernetes thay pod cũ bằng pod mới từng phần:

`Old version: 3 pods
New version: 0 pods

↓ deploy

Old version: 2 pods
New version: 1 pod

↓ deploy

Old version: 1 pod
New version: 2 pods

↓ deploy

Old version: 0 pods
New version: 3 pods`

Trong khoảng thời gian này, **old và new version cùng chạy**.

Do đó:

`- API contract phải backward compatible.
- Event schema phải backward compatible.
- Database schema phải compatible với cả old/new code.
- Không drop/rename column ngay ở release đầu.`

### **Expand/contract migration**

Ví dụ đổi từ `status` cũ sang state model mới.

`Release 1 — Expand:
- Thêm column hoặc enum/status mới.
- Không xóa column cũ.
- Old version vẫn chạy được.

Release 2 — Compatibility:
- New code hiểu cả status cũ và status mới.
- Có thể dual-write / backfill theo nhu cầu.
- Theo dõi data consistency.

Release 3 — Cutover:
- New code đọc state model mới.
- Canary rollout.
- Theo dõi error rate, stuck order, status mismatch.

Release 4 — Contract:
- Sau rollback window và data verification,
  xóa logic/schema cũ.`

### **Rollback plan**

Rollback cần trả lời:

`- Rollback application image có còn đọc schema mới được không?
- Dữ liệu mới ghi ra có compatible với code cũ không?
- Có feature flag để tắt logic mới không?
- Có data repair script cho order stuck không?
- Khi nào rollback canary?`

Ví dụ trigger rollback:

`- Checkout 5xx > 1% trong 5 phút.
- p95 checkout > 800ms trong 10 phút.
- PAYMENT_PROCESSING stuck tăng bất thường.
- Readiness failure trên nhiều pod.
- Consumer lag/outbox backlog tăng liên tục sau release.`
